AI TEACHING ASSISTANT
PROJECT ARCHITECTURE AND INTERVIEW PREPARATION GUIDE

This guide explains the implementation currently in the repository. It is designed to help you
present the project accurately in an interview. Be honest about the limitations in Section 9;
this is a useful working prototype, but it is not yet a fully authenticated, horizontally scalable
production service.

======================================================================
1. PROJECT IN ONE SENTENCE
======================================================================

This is a Streamlit educational video question-answering app that extracts speech from a selected
video, transcribes it into timestamped chunks, checks whether the transcript appears educational,
embeds and indexes the chunks in ChromaDB with video/session metadata, and answers questions using
retrieved transcript context through a Groq-hosted language model.

======================================================================
2. SHORT INTERVIEW INTRODUCTION
======================================================================

30-second version:

"I built an educational video assistant with Python and Streamlit. Users can upload a video or
provide a supported video link. MoviePy extracts the audio, Whisper transcribes it into timed
segments, and I group those segments into chunks. The transcript is checked for educational
content. Accepted chunks are embedded using Sentence Transformers and stored in QdrantDB with
video_id, session_id, and timestamps. For each question, I filter vector search by the active
video and session, then send only the retrieved transcript chunks to a Groq model to generate a
grounded answer. I also addressed stale context by making processing per-video and adding metadata
filters, and I wrote tests for video/session isolation and reprocessing."

Short version of the key bug:

"The app used to answer from the first video because it reused fixed audio/transcript filenames,
skipped indexing when the shared Chroma collection already contained data, and retrieved without a
video filter. I fixed the underlying data flow by using per-video artifacts, storing session/video
IDs on each chunk, and requiring both IDs in every retrieval."

======================================================================
4. END-TO-END REQUEST FLOW
======================================================================

A. Video input

1. app.py accepts MP4, MOV, AVI, WEBM, or MKV uploads, or a supported HTTP/HTTPS URL.
2. yt-dlp downloads a URL. An uploaded file gets a SHA-256-based filename; each URL download gets
   a unique UUID-based filename.
3. Each Streamlit browser session gets a UUID session_id in st.session_state. Web source videos
   are stored under input_videos/<session_id>/, so the UI lists that session's own files.
4. When a file is selected, app.py associates a video_id with that path in the current Streamlit
   session. The user clicks Process.

B. Audio and transcription

5. convert_video_to_mp3(video_path, audio_path) checks the source, removes stale output if present,
   extracts audio with MoviePy, closes the clip, and checks that the output is nonempty.
   The output path is output_data/<video_id>.mp3.
6. transcribe_and_optimize_chunks(audio_path, json_path) removes an old transcript, loads the
   Whisper base model, transcribes the audio, and combines timed speech segments until the text
   reaches about 400 characters. It records each chunk's start/end seconds.
7. An empty transcript raises a clear error; the application does not fall back to old transcript
   content. Fresh chunks are saved to output_data/<video_id>.json.

C. Educational classification

8. classify_educational_content joins the chunk text and rejects transcripts shorter than 20 words.
9. Otherwise it sends up to the first 12,000 characters of transcript plus a supplemental title to
   Groq. The model is asked for JSON containing an educational boolean and a short reason.
10. If rejected, the UI shows:
    "This video does not appear to contain educational content. Please provide an educational
    video to continue."
    A rejected video is not activated for chat.

D. Indexing

11. Accepted chunks are passed to store_chunks_in_chroma. The function opens the persistent
    ChromaDB collection named video_lectures under vector_db/.
12. It deletes only records matching both the current session_id and video_id. This replaces stale
    chunks for that exact video/session when reprocessing without wiping unrelated records.
13. all-MiniLM-L6-v2 creates embeddings for the chunk texts. Chroma stores the document, embedding,
    timestamp metadata, video_id, and session_id. Chunk IDs include session, video, and chunk index.

E. Question answering

14. Chat messages live in Streamlit session state. Selecting another video clears chat and
    deactivates the old video until the new selection is processed.
15. The retrieval query combines the current question with up to six earlier user questions. This
    helps a follow-up like "Why is that important?" retrieve the topic of the earlier question.
16. retrieve_top_chunks embeds the query and asks Chroma for up to five chunks filtered by BOTH
    active video_id and session_id.
17. generate_ai_tutor_response receives the current question, retrieved text/timestamps, and up to
    eight recent chat messages. The history may clarify a reference, but the prompt says it cannot
    be used as evidence for facts.
18. If retrieval returns no chunks, the LLM is not called. The exact response is:
    "The answer to this question was not found in the provided video's content."
19. If chunks are returned but do not support the answer, the LLM is instructed to return the same
    fallback and not invent facts or timestamps. This latter behavior relies on model instruction-
    following, not a formal guarantee.

======================================================================
5. FILES AND RESPONSIBILITIES
======================================================================

app.py - Streamlit web interface and orchestration

- Upload, URL download, video selection/deletion, progress display, and chat.
- Maintains session_id, video IDs, active video, and chat in Streamlit session state.
- Stores web source files under a session-specific input folder.
- Calls media extraction, transcription, classification, indexing, retrieval, and answer functions.
- Clears chat when selected video changes and catches processing/chat errors for UI display.

transcribe.py - media preprocessing

- convert_video_to_mp3(video_path, audio_path): MoviePy audio extraction and output checks.
- transcribe_and_optimize_chunks(audio_path, json_path): Whisper, timed chunk creation, and
  empty-transcript handling.
- The target chunk length is about 400 characters, not a tokenizer-measured token count.

rag_pipeline.py - classification, vector database, and LLM functions

- _get_groq_client(): uses GROQ_API_KEY from environment/.env or Streamlit Secrets; fails explicitly
  if no key exists.
- _get_embedding_model(): lazily loads and caches all-MiniLM-L6-v2 within the Python process.
- get_chroma_collection(db_path): opens or creates the persistent video_lectures collection.
- classify_educational_content(...): transcript-based classification and JSON validation.
- store_chunks_in_chroma(...): scoped deletion and vector upsert with metadata.
- retrieve_top_chunks(...): query embedding and metadata-filtered nearest-neighbor search.
- generate_ai_tutor_response(...): answer prompt, same-video history, timestamp formatting, and
  empty-context abstention.

main.py - command-line runner

- Asks for a local video filename in input_videos/.
- Generates new UUID session/video IDs for that run.
- Runs extraction, transcription, classification, indexing, retrieval, then answers one question.
- It is a one-question terminal flow, not the multi-turn Streamlit chat.

Other useful files

- requirements.txt: Python packages including Streamlit, ChromaDB, Groq SDK, Whisper, MoviePy,
  Sentence Transformers, python-dotenv, and yt-dlp.
- packages.txt: FFmpeg system package for Streamlit hosting.
- .env.example: safe API-key placeholder template.
- .gitignore: excludes environment secrets and local data folders.
- Readme.md: setup, deployment, architecture summary, and limitations.
- projectF.txt: detailed project notes and implementation explanation.
- tests/test_video_isolation.py: regression coverage for retrieval, metadata, reprocessing,
  classification boundaries, transcript behavior, and secret access.

======================================================================
6. TECHNOLOGIES AND WHY
======================================================================

Python
  Main language for the UI, media processing, retrieval, and LLM orchestration.

Streamlit
  Python-based web interface and per-browser-session state without a separate frontend/API server.

yt-dlp
  Downloads supported online videos. Platform changes or restrictions can still make a download
  fail.

MoviePy and FFmpeg
  MoviePy opens the video and extracts audio; FFmpeg performs the underlying media conversion.

OpenAI Whisper base
  Speech-to-text model that runs in the app's Python process and returns transcript segments with
  timestamps. The video itself is not sent to Groq in this audio-transcription path.

Sentence Transformers: all-MiniLM-L6-v2
  Local embedding model for transcript chunks and questions. Vector similarity helps match
  semantically related text even when the words differ.

ChromaDB
  Vector store for transcript documents, embeddings, metadata, and nearest-neighbor retrieval.
  This project uses its local persistent database under vector_db/.

Groq API: openai/gpt-oss-120b
  Hosted language-model API used for transcript classification and answer generation. The app
  calls the Groq API; it does not host the LLM itself.

python-dotenv / Streamlit Secrets
  Loads a local .env in development and Streamlit Cloud Secrets in deployment. Never commit a real
  API key.

======================================================================
7. RAG CONCEPTS TO EXPLAIN
======================================================================

RAG means Retrieval-Augmented Generation. The app first finds relevant material from the active
video and then gives that evidence to a language model to compose an answer.

Ingestion:
video -> audio -> transcript -> chunks -> embeddings -> Chroma records.

Question time:
question -> query embedding -> metadata-filtered vector search -> transcript context -> LLM answer.

Embedding:
A numeric vector representing semantic features of text. Similarity between question and chunk
vectors helps find relevant passages without relying only on exact keyword matching.

Chunk:
A bounded transcript passage used as one retrieval unit. Grouping short Whisper segments provides
more context than indexing every sentence separately. Smaller chunks may improve precision but lose
context; larger chunks preserve context but can be less precise and consume more prompt space.

Metadata filter:
Structured fields attached to a record. Here Chroma requires session_id AND video_id to match
before a chunk can be returned. This prevents a different video's nearest vector from entering the
active retrieval context.

Top-k:
The maximum number of results to retrieve. The Streamlit UI asks for five chunks.

Grounding:
Constraining factual answers to supplied evidence. This app uses filtered retrieval, transcript
context, and prompt instructions. This reduces unsupported answers but cannot mathematically
guarantee that an LLM never hallucinates.

======================================================================
8. ORIGINAL BUG AND ROOT-CAUSE FIX
======================================================================

Original causes:

1. Every video used the same audio output path and transcript JSON path.
2. Transcription could load the old JSON transcript instead of processing current audio.
3. Indexing skipped work when the shared Chroma collection contained any data.
4. Chunk IDs were generic and chunks did not identify their source video/session.
5. Retrieval searched the collection without video/session filters.
6. The UI did not bind chat/retrieval tightly enough to the active processed video.

Fix:

1. Use video-specific audio and transcript filenames and regenerate artifacts on processing.
2. Attach session_id, video_id, and timestamps to every indexed chunk.
3. Use chunk IDs containing session/video/chunk index.
4. Replace only the matching session/video's Chroma records during reprocessing.
5. Require both active IDs in every retrieval query.
6. Clear/deactivate chat when selection changes; enable Q&A after successful processing.

The fix isolates the data instead of deleting the whole database or simply changing a prompt.

======================================================================
9. LIMITATIONS AND HONEST PRODUCTION READINESS
======================================================================

Be candid in an interview. These are current limitations, not features to claim as solved.

1. Transcript-only understanding: this pipeline does not inspect video frames, slides, diagrams,
   or on-screen code. A future multimodal version could extract timestamped frames and use OCR or
   vision embeddings alongside transcript chunks.
2. Educational classification is LLM-based and can misclassify. It uses the transcript as primary
   evidence and asks for conservative JSON, but it is not a validated moderation classifier.
3. Transcript classification considers up to the first 12,000 characters. It may miss educational
   content later in a long video.
4. If retrieval is empty, the not-found answer is deterministic. If irrelevant chunks are returned,
   the fallback depends on the LLM obeying the prompt.
5. There is no explicit similarity-score threshold or reranker. The top five nearest filtered
   chunks are returned even when relevance is weak.
6. Unit tests mock Whisper and Groq calls. They do not prove live model quality or exercise a full
   real-video download -> transcription -> classification -> answer flow.
7. Session UUIDs are Streamlit session state, not persistent identity. The app has no user login,
   authorization system, or server-side tenant database.
8. Chroma and files use local disk. Streamlit Cloud local storage may be lost after restart or
   redeployment. The repository does not configure durable object storage or a managed vector DB.
9. Processing is synchronous in the Streamlit request. Long recordings block that session.
   There is no task queue, worker pool, distributed processing, or rate limiting.
10. Whisper and embedding models use CPU, RAM, disk, and download bandwidth. Large videos or many
    concurrent users may exceed free-host resource limits.
11. Dependencies are not tightly version-pinned; production deployment should test and pin a
    compatible set.
12. yt-dlp supports only extractors/platform behavior that continue to work; access restrictions
    can cause download failures.

Security and privacy facts:

- GROQ_API_KEY belongs in local ignored .env or Streamlit Cloud Secrets, never in source control.
- Video files are held on the application host while processed.
- Transcript text is sent to Groq for classification and answer generation.
- This transcript RAG path sends transcript text to Groq, not the complete video file.
- Random IDs and filters are application-level isolation, not a substitute for authentication,
  authorization, or secure database tenancy.
- Treat a deployed Streamlit link as public unless access has explicitly been restricted.

========================================================================
10. LIKELY INTERVIEW QUESTIONS AND ANSWERS
========================================================================

Q1. Explain the architecture.

A. "Streamlit handles input and session state. MoviePy and FFmpeg extract audio; Whisper generates
timed transcript segments; I group those into chunks. Groq classifies the transcript. For accepted
content, Sentence Transformers generates embeddings and Chroma stores chunks with session/video
IDs and timestamps. At question time I filter vector search by both IDs and send retrieved
transcript evidence to Groq to generate an answer."

Q2. What was the hardest bug?

A. "The app answered using a previous video. I traced it to fixed transcript/audio paths,
collection-wide skip logic, and retrieval without metadata filters. I fixed the data model and
query contract instead of clearing the whole database: video-specific outputs, metadata on every
chunk, scoped reprocessing, and filtered retrieval."

Q3. Why RAG instead of sending the whole transcript to the LLM?

A. "Retrieval selects a small set of relevant passages, keeping the prompt smaller and tying the
answer to localized transcript evidence and timestamps. It is more efficient than resending an
entire long transcript for each question."

Q4. Why embeddings?

A. "They make semantic retrieval possible when the question and transcript express the same idea
with different words. The same embedding model encodes both chunks and query."

Q5. How do you prevent cross-video retrieval?

A. "Every chunk has a video_id and session_id, and every Chroma query requires both to match the
active state. Reprocessing deletes only the same pair. The chat is cleared when video selection
changes."

Q6. Is it secure multi-tenancy?

A. "It provides application-level isolation using random IDs and filtered queries, and the UI
stores each session's source files in its own folder. It is not a full identity or authorization
system. I would add authentication, server-side tenant mapping, and managed storage before claiming
production multi-tenancy."

Q7. How do you decide if a video is educational?

A. "I reject empty transcripts and require at least 20 words before classification. Then I send
transcript text as primary evidence to a Groq model and ask for structured JSON. The title is only
supplemental. Since an LLM can misclassify, I would evaluate it on a labeled dataset before using
it as a strict production policy."

Q8. What if the answer is not in the video?

A. "If retrieval returns no chunks, the app directly returns the exact not-found response without
calling the model. If some chunks are returned, the prompt tells the model to answer only when
they support the answer. That second case remains prompt-based; I would add a relevance threshold
and output/evidence validation."

Q9. How are timestamps preserved?

A. "Whisper segments have start/end seconds. The chunker stores the first segment's start and last
segment's end. Those values go into Chroma metadata and are formatted as MM:SS in the answer
context."

Q10. How does follow-up chat work without using history as evidence?

A. "The UI keeps messages for the active Streamlit session and clears them when the selected video
changes. Earlier user questions are joined with the current question for retrieval, and recent
messages are included to resolve references. The prompt says history is not factual evidence;
retrieved transcript chunks are."

Q11. Why ChromaDB?

A. "It provides a simple Python API for persistent local vector storage and metadata-filtered
similarity search. It fits this prototype. For multiple app instances and durability I would move
to a managed vector store."

Q12. What happens when a video is reprocessed?

A. "Audio and transcript are regenerated. Before indexing, I remove only the Chroma records for
that session/video pair, then upsert the new chunks. Other videos and sessions are preserved."

Q13. How do you handle failures?

A. "Missing API keys, invalid URLs, download failures, missing audio, empty transcripts,
classification errors, vector-store errors, and LLM errors are surfaced to the UI/CLI. The
application does not silently answer from an old transcript."

Q14. What would you improve next?

A. "I would add measured relevance thresholds or a reranker, dataset-based classification and
answer evaluation, background workers, upload limits and rate limits, monitoring, user
authentication, durable object storage, a managed vector DB, and pinned dependencies. For visual
questions, I would add timestamped frame/slide extraction and multimodal retrieval."

Q15. How did you test it?

A. "The unittest suite checks metadata filters, isolation of multiple videos and sessions in a real
ephemeral Chroma collection, scoped reprocessing, insufficient transcript rejection, empty-context
fallback, the Streamlit secret path, and fresh audio/transcript outputs. Whisper and Groq are
mocked, so these tests do not establish live model accuracy."

Q16. Is it production-ready?

A. "It is a working prototype with a corrected ingestion/retrieval isolation path. I would not
call it production-ready for arbitrary public traffic yet because it needs authentication,
durable storage, resource controls/background jobs, monitoring, measured quality, and stronger
answer validation."

======================================================================
11. QUICK DEFINITIONS
======================================================================

Transcript: text recognized from spoken audio by speech-to-text.
Chunk: a bounded transcript section used as one retrieval unit.
Embedding: a numeric representation of text used for semantic similarity.
Vector database: a system that stores/searches embedding vectors; this project uses ChromaDB.
Metadata: structured fields attached to a vector record; here IDs and time ranges.
Top-k: maximum number of nearest chunks requested; the web UI uses five.
Grounding: restricting factual answers to provided evidence; not a mathematical guarantee here.
Hallucination: an unsupported or fabricated model claim.
Session state: temporary Streamlit browser-session data, not a persistent user account/database.

======================================================================
12. RUN AND TEST THE PROJECT
======================================================================

Prerequisites:

- Python dependencies installed with: python -m pip install -r requirements.txt
- FFmpeg installed and available on PATH.
- GROQ_API_KEY set in local .env (copy .env.example) or Streamlit Cloud Secrets.

Run the web UI:
streamlit run app.py

Run the CLI:
python main.py

Run regression tests:
python -m unittest discover -s tests -v

Before an interview demo, test with a short, non-sensitive educational video. Ask one question
whose answer is explicitly spoken, then an unrelated question. Do not claim a measured accuracy
percentage unless you have run a documented evaluation.

13. PRESENTATION ADVICE
======================================================================

- Start with the problem and user flow, then explain the pipeline.
- Clearly separate ingestion (video -> transcript -> embeddings), retrieval (filtered vector
  search), and generation (LLM answer from retrieved evidence).
- Explain that both video_id and session_id are part of the retrieval contract.
- Describe the original root cause and why a prompt-only change would not have fixed stale data.
- Mention what your tests cover and what they do not cover.
- Be honest about transcript-only scope, LLM uncertainty, missing authentication, and temporary
  cloud storage. This demonstrates engineering judgment instead of overclaiming.
